readme: Entity, person and relationship statementIds are now content-addressed, so a record that changes gets a new statementId and keeps its recordId, as BODS v0.4 asks.
tests: backend +15

Phase B, step 2, of the "Improving alignment with BODS record ID requirements" ticket (phase A was Phase 396; step 1 the record-id references phase). BODS v0.4 wants a `statementId` unique per statement and a `recordId` stable across a record's versions; since Phase 1 OpenCheck's factories set the two equal for entities and people, so a record that changed between two runs kept its id and two readings of one record could not be told apart. Now `recordId` is what it was — `_stable_id(source, kind, local id)`, so every key, cache and test fixture still works — and `statementId` is `_stable_id(recordId, "content", digest)` where the digest covers `recordDetails` (minus `publicListing`, which the listing stamps on a copy after the sources settle) and `recordStatus`; annotations, `statementDate` and `retrievedAt` are outside it (Stephen's decisions, 23 Oct 2026), so a re-read that found the same record publishes the same statement and a re-read that found a change publishes a new one. A relationship's `statementId` follows the same rule, replacing the closed-variant salt. Relationships name their parties by `recordId` throughout (every mapper and the three predicted-id sites in `risk.py` read `recordId` now; the FtM subject-level signals had predicted a two-part id no mapper ever wrote, so SANCTIONED/PEP evidence never found its node — fixed). Because the engine predicts a party's `recordId` and every consumer keys on `statementId`, `bods/refs.py::resolve_signal_references` resolves every evidence reference (`statement_id`, `subject_statement_id(s)`, `matches[]`, `jurisdictions[]`, `longest_path`, `ended_relationship_statement_ids`) through the Phase 210 resolver at one chokepoint, inside `_merge_signals` (both lookup pipelines, `/report`, the FullCheck hop) and on `/deepen`. A mapper that edits a statement after the factory — a register status, a legal-form label, an account prefix stripped — would leave a stale id, so every `map_*` is `@content_addressed` (`bods/statements.py`): the id is recomputed as each statement leaves the mapper, generators stay lazy (the Phase 314 scope rule is unchanged), another publisher's statements (no `opencheck-` recordId) are untouched; `apply_register_status` and the state-body classifier refresh in place too. Three guards: the conftest mapper guard fails any yielded statement whose id is stale, the weekly BODS quality sweep gains `stale_statement_id`, and `unique_statements` dedupes parties on `recordId` (a later reading of one record wins, as the old statementId dedup did when the two were equal) while relationships still dedupe on `statementId`. FullCheck's blunt string remap (`routers/expand.py::_anchor_replacements`) rewrites both ids of each subject statement onto the anchor — the minimal change Stephen chose; the structured remap is its own ticket. The frontend needed no code change: the graph, tree, reconciler and badges already resolve through `bodsRefs.ts` (step 1's harness proved it), and the mirror-vs-live GLEIF test now compares minus `statementId`, since trimmed identifiers move it. To check in production: a QuickCheck of Ørsted should show `statementId ≠ recordId` on every OpenCheck statement, the SANCTIONED/PEP badges on an OpenSanctions subject node, and `/signalstats.declaration_subject` still without `unresolved`; then regenerate the six curated narratives once (they quote statement ids). Decision logged on the ticket: the resolver keeps two tiers (statementId, recordId) and no `declarationSubject` alias — the BODS MUST is about what a statement contains, which the Phase 396 stamp satisfies, not a lookup path.
