The first run of *Refresh BCE Belgium index* on `main` (29 Oct 2026, after Phase 421 merged) logged in, read the files listing and refused: "no KboOpenData_*_Full.zip on the files listing". The cause was the file name: the KBO portal now publishes a full file beside every day's update, named with the day — `KboOpenData_0518_2026_10_20_Full.zip` — and `build_bce_belgium_index.py`'s pattern expected the cookbook's monthly `KboOpenData_<n>_<yyyy>_<mm>_Full.zip`. `FULL_ZIP_RE` accepts both shapes; the highest extract number still picks the newest file and the cut is still KBO's `SnapshotDate` from `meta.csv`. The row floors were measured against the real register: the 29 Oct 2026 full file has 1,265,258 denomination rows (a natural-person enterprise files no denomination), so `MIN_ROWS` is 1,000,000 for each of the three CSVs and the workflow's named-entity floor is 1,000,000, where the cookbook's headline figures had refused the real file. On a refusal the builder now logs what the portal served — the final URL, the HTTP status, the page title and every link on the page, never the credentials or the session — which is how the name change was read off run 40967415746. Verified by `workflow_dispatch` runs of the workflow on the branch: 40967565582 (the name fix alone) still refused on the row floors, and 40969223885 on the head commit built and published the first `bce-belgium-index` asset (`bce_belgium.sqlite.gz`, 125 MB, 23:00Z). To check in production: after the backend's next boot, Proximus (`549300CWRXC5EP004533`) shows the Belgium card with a dated snapshot chip and GLEIF's `BE-BCE_KBO` identifier corroborated.
