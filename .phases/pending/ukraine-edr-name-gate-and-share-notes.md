Two Ukraine ЄДР tickets, one branch. **The name gate.** The ЄДР publishes no birth date, so its 674,413 beneficial owners and its founders reach the related-party screens with a name alone, and the Phase 106 birth-year corroboration can never fire for them. A Ukrainian name carries a patronymic, so `cross_check._patronymic_compatible` now drops a person match when both names carry one and none of the record's forms — caption, aliases, previous names, FtM `fatherName` — names the same father (`names.patronymics_conflict`). Stephen's decision (31 Oct 2026): reject only a clear conflict. OpenSanctions often spells a Ukrainian patronymic in its Russian form (ВОЛОДИМИРОВИЧ → "volodimirovich" against "Vladimirovich", 0.59 similar), so `names._father_key` folds the Ukrainian and Russian spellings of one given name together first (Volodymyr/Vladimir, Serhii/Sergei, Mykola/Nikolai, Yevhen/Evgenii, the h/g and y/i letter pairs, doubled letters, trailing vowels), and a record with no patronymic keeps the match. Agreeing patronymics are not corroboration: the match still reads "Possible name match only". It applies to every person target on the OpenSanctions, EveryPolitician and OpenAleph screens. The ICIJ screen's Phase 282 person-token rule folds the same spellings, so it no longer rejects a Russian-spelt patronymic as a different token. Not done: the per-source confidence cap (option 3), and the 500-lookup measurement (option 4), which would pull CC BY-NC data at volume. **The share notes.** Both founder-share `transformation(...)` calls in `bods/mappers/ukraine.py` passed the sentence as the pointer and the pointer as the description. The pointer was also built as `pointer("/recordDetails/interests/0/share")`, which escapes every `/` to `/~1recordDetails~1…`, so a plain swap would still have been wrong. One helper, `_derived_share_note()`, now builds the note by keyword on `/recordDetails/interests/0/share`, and the "As filed" toggle finds it. lib-cove-bods checks annotation pointers on entity statements only, so nothing caught the error on these relationship statements. `validator.annotation_pointer_issues` now checks every record kind: in the conftest mapper guard (it found no other mapper at fault across the whole suite) and in the weekly BODS quality sweep as `annotation_pointer_invalid` (fail). After deploy: the next sweep on a Ukrainian subject shows no `annotation_pointer_invalid`, and a ЄДР lookup's "As filed" toggle shows the derived-share note on a founder's percentage.
