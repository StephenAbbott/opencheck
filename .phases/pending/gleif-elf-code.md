---
OpenCheck already vendored GLEIF's ELF code list (v1.6, 3,446 codes) and resolved `entity.legalForm.id` to the `legalFormLabel` words the AMLA trust rule, the subject profile and the RDF export read, but the four-character code itself was dropped — no BODS statement said `B6ES`. `map_gleif` now writes it as `recordDetails.legalFormCode` (`elf.elf_code`: upper-cased, four alphanumerics, never GLEIF's placeholders 8888 / 9999; a well-formed code missing from the vendored list is still carried, since it is GLEIF's assertion and the list updates twice a year). Stephen's decision (13 Nov 2026), after the ask to use `identifiers` was challenged: an extension, not an identifier — BODS v0.4 defines an Identifier as one "assigned to a person or entity", an ELF code names a form thousands of entities share, and every identifier key merges entities in `reconcile._identifier_keys` (every UK private company, `H0PO`, would have become one node); a test pins that two companies of one form share no identifier key. Registered in the data dictionary's `EXTENSIONS` and carried in the sample bundle; the RDF export writes `oc:legalFormCode` (BODS has no term). `search_filters.PLACEHOLDER_FORMS` now reads `elf.PLACEHOLDER_CODES`. The GLEIF statements' content-addressed `statementId`s move once with the new field. After deploy, Shell plc's GLEIF statement should read `"legalFormCode": "B6ES"`.
