Option C of the "PermID publicListing can be written onto Open Ownership's verbatim GLEIF statement" ticket, spun out of the integrated-ownership pointer fix (PR #467). `listing.apply_to_bods` picked the first subject statement whose `consistency.source_id_of` was `gleif`, else the first statement carrying the LEI at all; Open Ownership's stored GLEIF statements (the curated `bulkBods` examples, BP and Rosneft among them) carry no stamped id and the description "GLEIF", so the listing could land in another publisher's `recordDetails` — against the Phase 317 rule never to patch another publisher's statements. The target is now `listing.own_gleif_target`: an entity statement carrying the LEI, stamped `source.opencheckSourceId: "gleif"` and published by OpenCheck. There is no fallback, unlike `integrated_ownership.annotation_target`: the listing writes a field into `recordDetails`, a bigger change than an annotation. Without OpenCheck's own GLEIF statement the BODS carries no `publicListing`; the `listing` event, the page line, the report and the MCP `listing` field are unchanged. Saved reports rebuild their export from the frozen event, so they pick up the new target on their next export with no migration. No golden file expected `publicListing` on an Open Ownership statement; the pipeline test, whose seeded bundle is Open Ownership-shaped, now asserts the BODS carries no listing while the event does.
