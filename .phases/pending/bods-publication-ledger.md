The first three build steps of the ledger ticket ("BODS publication ledger: recordStatus 'updated' and a monthly time series"), from Stephen's six decisions of 17 Nov 2026: one GitHub release a month; changes only, no confirming statements; a mapper correction published as `updated` with a `correcting` annotation; a closed record that returns gets a new `recordId`; GLEIF only for the first edition; the edition dated the first of the month and built after the Golden Copy is regenerated.

`opencheck/bods/publication_ledger.py` is the ledger: one SQLite file holding, per record, the last statement published (id, a digest of `recordDetails`, status, edition, source, reading version) and its body. An edition is applied source by source and yields only the statements that say something new. `recordDetails` alone is compared, so a re-stamped record publishes nothing. `close_missing` closes what a source read whole no longer carries, with the last details published and a note, and refuses when it would close more than a tenth of a source's live records. A returning record starts a second life under a derived `recordId` and every reference to it in the edition is rewritten; parties must be applied before relationships. A `new` statement keeps the lookup's content-addressed `statementId`; `updated` and `closed` ids also carry the edition, so a record that goes back to an earlier state never repeats an id. Ids are held as 12 bytes and bodies deflated against a dictionary the file keeps, because the GLEIF layer is 16.7 million records.

`opencheck/bods/reading_versions.py` gives each series source a reading version. `tests/test_reading_versions.py` maps pinned Golden Copy bundles and compares a digest with `tests/fixtures/reading_pins/pins.json`: a change to `map_gleif`'s `recordDetails` fails until the version is bumped and `scripts/pin_reading_versions.py` re-run. That is what lets the ledger tell OpenCheck's changes from GLEIF's; diffing two published Estonia editions had found most "changes" were mapper fixes. `annotations.correcting` is new, and the data dictionary now describes the motivation instead of saying OpenCheck never writes it.

`scripts/build_bods_series.py` builds an edition from the Golden Copy mirror with no API call: every LEI mapped by the Estonia dataset's code path (each edge once, from the child; a parent's entity statement from the parent's own bundle), then the ledger, then numbered gzip parts, `manifest.json` and release notes. `.github/workflows/publish-bods-series.yml` runs it on the 2nd of each month, reads the ledger back from the newest `bods-series-*` release and publishes `bods-series-YYYY-MM` as a draft that is made public only when every asset is up. Reader's page: `docs/bods-series.md`.

A full trial build on the Golden Copy of 1 Nov 2026 took 54 minutes on four cores (14 mapping, 40 in the ledger): 3,481,100 LEIs, 16,652,420 statements (6,172,075 entity, 3,764,182 person, 6,716,163 relationship), 1.68 GB gzipped in five parts, a 4.25 GB ledger, and no relationship naming a party without a live record. On a 40,000-LEI trial a second edition over the same data published nothing, as it should. Twenty-six backend tests.
