`backend/scripts/sweep_estonia.py` is rewritten for the "Rebuild the Estonia dataset from the Golden Copy mirror and the RIK index" ticket. The GLEIF layer was Open Ownership's `gleif_version_0_4` parquet (statements to February 2025) and the register layer a July copy of four RIK files, joined on `EE-KMKR` (the VAT scheme). Now: the GLEIF layer is every LEI with legal jurisdiction EE in the Golden Copy mirror (`entity_pages.sqlite`; `--refresh-mirror` applies GLEIF's latest delta first with `mirror_refresh.apply_delta`), mapped with `map_gleif` from the bundle a lookup is served from (`GleifAdapter._snapshot_bundle`), so the statements carry `opencheckSourceId`, the mirror's two clocks, Phase 305 event dates and the Phase 255 LEI-status note. ACTIVE entities only unless `--include-inactive`; ANNULLED and DUPLICATE registrations are left out. Each GLEIF edge is published once, from its child (a lookup keys the same record `<child>:direct-parent:<parent>` from one side and `<parent>:direct-child:<child>` from the other); a foreign company consolidated by an Estonian one contributes only its own record and its edges to Estonian parents. The register layer is every LEI holder's RA000181 code plus the upward closure of Estonian corporate shareholders in the index (no depth or count cap), each mapped by `map_ariregister` on the index tier: current lists, off-card persons (supervisory boards, AS shareholders, founders), general data, rulings and pledges; the ended-ownership history is not read (it needs RIK's credentialed services; the dataset stays bulk-only). A company's own register record outranks the thinner statement another company's shareholder row builds under the same id. The layers join on `EE-ARIREGISTER`. Stages `select` / `gleif` / `register` / `assemble` / `check`; `check` fails the build on a dangling reference, a registry code under `EE-KMKR`, a valid personal identification code in a person's identifiers or annotations, or a person's street address, and `--libcove` adds lib-cove-bods. `register-missing.csv` lists the LEIs whose registry code the open data does not hold — on the 19 Oct 2026 build 429 of 29,086, every one checked a company the register has deleted while GLEIF still records it as active (414 of them LAPSED LEIs), so the July caveat cannot reach zero: the open data carries no deleted company. A mapper fix rode along: a foreign legal person named on an Estonian list got `https://ariregister.rik.ee/eng/company/<its foreign number>` as its source URL (`C 53839`, `HRB 153232` — not a URI, and not a page on the Estonian register); `_ee_company_url` now gives one only for an Estonian registry code. The new release is `dataset-estonia-2026-10-19`.
