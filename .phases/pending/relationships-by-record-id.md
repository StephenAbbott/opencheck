Phase B, step 1, of the "Improving alignment with BODS record ID requirements" ticket (phase A was Phase 396). BODS v0.4 says a relationship's `subject`, `interestedParty` and `componentRecords` hold a party's **recordId**; OpenCheck's factories have always written that, but because every mapper sets `statementId == recordId` a consumer that compared a reference against statementIds directly would never have noticed. Step 2 makes the entity and person `statementId` content-addressed (Stephen's decisions of 23 Oct 2026: a hash of `recordDetails` + `recordStatus`, annotations and dates excluded), so the two will differ on every statement. This step ships the proof first, on its own: `backend/tests/test_record_id_references.py` and `frontend/src/lib/recordIdReferences.test.ts` build a realistic lookup bundle (two sources, a three-layer GLEIF chain with component records, a person, a state owner, a trust, an ended holding), **scramble** it into step 2's exact shape — a different `statementId` on every entity and person, the `recordId` and every reference untouched — and run each consumer on both, expecting the same answer once ids are mapped back: the risk engine's structural rules, integrated ownership, the owners tools, subject identity and profile, record consistency, the knowability chain, possibly-same, graph shape, the related-party selector, the FtM / Senzing / Neo4j / RDF exports, the Markdown and HTML reports, the evidence packet, the validator and the quality sweep; on the frontend the graph, the tree, the reconciler, BackgroundCheck and integrated ownership. Every one passed as it stood — Phase 210's resolver (`bods/refs.py`, `bodsRefs.ts`) is what they read — so the harness changes no behaviour and records the contract. The one known exception, `routers/expand.py`'s string remap, is step 2's. The factory docstrings and five module comments that asserted `statementId == recordId` as a design premise now say what is true: a reference is a recordId, resolved, and the two ids need not be equal.
