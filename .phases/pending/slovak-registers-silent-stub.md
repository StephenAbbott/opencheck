Found by the BODS quality sweep of 26 Oct 2026 (`deepen_empty|rpo_slovakia`): production `/deepen?source=rpo_slovakia&hit_id=35815256` (Slovenský plynárenský priemysel, a.s.) answered after ~16 s with `{"is_stub": true}` and no statements, while the source-health sweep on GitHub Actions read the same record in 1.3 s an hour earlier. `RpoSlovakiaAdapter._get_list` caught every exception and returned `[]`, and `fetch` turned `[]` into a stub, so a register that did not answer read exactly like live mode switched off: no `source_error`, no degradation, and a Slovak lookup that said nothing about the gap. `rpvs_slovakia`, which shares the `sk_ico` key, had the same shape in its resolve step and its partner read. Probed on 26 Oct 2026 from the cloud: `api.statistics.sk` itself answers (root 404 in 1.5 s), but `/rpo/v1/search` (by IČO and by name) hangs with zero bytes past 40 s — an application-level hang for datacentre ranges, which Render's ~16 s is the shared 15 s read timeout firing on; RPVS answered in 1 s. Now both adapters raise a timeout, an HTTP error or an unreadable body instead of swallowing it; the pipeline turns it into a `source_error` and a `source_fetch` degradation (reason `timeout` for a timeout, Phase 241) and the card offers a retry; nothing is cached on failure (Phase 262); and an empty answer — not in RPO, not an RPVS public-sector partner — is cached with `put_absent`, so it expires, where it used to be an everlasting empty list. `/deepen` on a failure now errors rather than returning an empty stub. A longer timeout or a retry would not fix a hang; whether to move RPO to an off-datacentre index (the JAR Lithuania route, Phase 325) is left open until production shows how often it fails. After deploy: re-dispatch the BODS quality sweep — `deepen_empty|rpo_slovakia` should be gone, replaced by a deepen error if Render still cannot reach RPO — and look up an SK LEI to see the degraded card.
