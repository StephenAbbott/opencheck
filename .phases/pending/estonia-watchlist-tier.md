---
title: The watchlist gains a third tier — a watched Estonian company is re-run when the e-Business Register's own daily data shows its people, name, status or legal form changed.
readme: A watched Estonian company is now re-checked when the e-Business Register's daily open data shows a change to its shareholders, board, beneficial owners, name, status or legal form.
tests: backend +32, vitest +5
---
Until now the watchlist re-ran a company only when GLEIF's Golden Copy delta or OpenSanctions' entity delta named it, so a watched Estonian company whose shareholders or beneficial owners changed on the register waited until GLEIF noticed something. Estonia is the one register OpenCheck rebuilds whole every day, so the refresh workflow now downloads the build it is about to replace and diffs it against today's (`scripts/diff_ariregister_index.py`, standard library, about 40 s on the real 380,000-company index). Per registry code it hashes the four people lists — persons on the registry card, shareholders (with the AS shareholders recorded off the card), beneficial owners, supervisory board — and compares the name, status and legal form (Stephen, 16 Oct 2026). Addresses, VAT numbers, capital, card entries, founders and auditors are not changes, and a row re-registered with the same content is not either (`kirje_id` is out of the digest). A list's change is its row count before and after, never the people in it, so no person reaches the watchlist store. Each day is appended to `ariregister-delta.json`, a rolling fourteen-day file uploaded beside the index after it; a day touching more than 10 % of the register (and over 1,000 companies) is kept as a summary marked suspect. The backend now re-checks the index asset hourly (`ARIREGISTER_REFRESH_INTERVAL_S`) — before this a new index landed only when the server restarted, so a re-run would have read yesterday's record — and swaps the file without closing a connection a lookup may be using. The worker's `ariregister_tick` reads the delta once the server holds a newer index than the last day read, maps each watch to its registry code (GLEIF's `registeredAs` under RA000181, else the baseline's `EE-ARIREGISTER` identifier), merges several days into one trigger and queues a re-run on the new `register` tier. Because a shareholder change moves no signal or status, a register entry is written even when the re-run finds nothing else (the Tier 2 rule, Stephen's decision): "The Estonian e-Business Register recorded a change to this company in its open data of 2026-10-17 (registry code 10421629)" then "Shareholders: 3 → 4 entries." The first run marks the current day without backfilling; a day the file cannot account for (a build not diffed, a broken chain, a suspect day) is a gap answered by a catch-up re-run of every watched Estonian company; a delta file older than the index is waited for. The feed, the page (chip "Register change", the register's lines under the trigger sentence) and the honesty line say it; `docs/watchlist.md` describes the third tier. After deploy: the next refresh run diffs against the asset it replaces and publishes `ariregister-delta.json` with its first day (the log prints the counts per list — the first real measure of how much the register changes a day); the worker's first tick only marks the day the server holds, so the first re-runs come from the day after. Watch `/watchstats` for `ee_last_cut`, `ee_days_read` and `ee_gaps`.
