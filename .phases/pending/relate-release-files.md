Step 5 of the ticket "Check out relate from Neo4J": Stephen chose (24 Nov 2026) to publish a `.rl` file beside the bulk zips as a convenience, with the Relate version recorded and the BODS JSON Lines file kept as the record. `backend/scripts/build_relate_file.py` writes the graph with `bods-neo4j to-cypher`, runs each statement through the `relate-db` binding with `DO_NOT_TRACK=1`, reads the node and relationship counts back per label and per edge pattern and refuses, writing nothing, when Relate rejects a statement or a count differs from the script's header (bods-neo4j PR #6 made the header count the edges MERGE makes). It gzips the file and writes a `.rl.json` manifest (Relate and bods-neo4j versions, counts, source and file SHA-256). `.github/workflows/publish-relate-file.yml` (run by hand with a release tag and its `.jsonl.gz`) pins relate-db 1.2.0 and bods-neo4j `aeb8346`, builds the file and adds both assets with `replace_release_asset.sh`, manifest last. Measured in the sandbox: the Laundromat release loads in 7 s to 2.5 MB gzipped (25 MB open), identical to the driver route's graph; Estonia in about 6 minutes to 66 MB gzipped (173 MB open), which opens in about 13 s. `docs/datasets.md` and the due-diligence skill's `bulk-datasets.md` and `graph-queries.md` name the file, and the skill now says that in the bulk graphs a GLEIF reporting exception is a `:Person`/`:Entity` hub, not `:UnspecifiedParty`. After merge: run the workflow for `dataset-estonia-2026-10-25` (`estonia-2026-10-25.jsonl.gz`) and `dataset-azerbaijani-laundromat-2026-10-06` (`azerbaijani-laundromat-2026-10-06.bods.jsonl.gz`).
