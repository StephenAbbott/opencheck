Found by the Phase 401 production check (Notion "Structured id remap for the FullCheck anchor collapse", 25 Oct 2026). A sweep of every id-bearing evidence key in production signals for Ørsted, Equinor and Shell plc found two that `refs.SIGNAL_REFERENCE_FIELDS` did not name. (1) `RECORD_CONSISTENCY.evidence.subject_statements[]`: its key matches neither the `statement_id` nor the `…statement_ids` rule, so Phase 401's structured remap left the collapsed ids there after a FullCheck hop, where the old string replace had rewritten them. Every surviving id in the Ørsted and Equinor hops was in this field. (2) `GLEIF_REPORTING_EXCEPTION` / `OPAQUE_OWNERSHIP` `evidence.exceptions[].statement_id`: the same bridge id is written to `exceptions[]` and `matches[]`; Phase 398's `resolve_signal_references` resolved `matches[]` to the statementId and left `exceptions[]` on the recordId, so one node had two ids in one signal (2 unresolved references per company in a plain `/lookup`). Both are now named (`("subject_statements", "list")`, `("exceptions", "list_of_dicts")`), so the resolver and the remap read them. Nothing consumed either field (the graph badges read `matches[]`; `subject_statements` has no reader), so nothing on the page changes. The tests use the production shapes and fail without the fix, and the field-list pin in `test_expand_structured_remap.py` now includes both. After deploy, the check is the same one as before: on Ørsted's and Equinor's `/expand-layer` hops, no collapsed id should be left outside the remapped fields, and a `/lookup` GLEIF exception signal's `exceptions[].statement_id` should equal its `matches[].statement_id`.
