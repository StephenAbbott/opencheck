readme: The Belgian Crossroads Bank for Enterprises joins the lookup as a monthly index of the KBO Open Data full file, built by a workflow with the portal's free login.
---
Phase 35 built `bce_belgium` against a hand-built local file (`extract_bce.py`, columns guessed, `BCE_BELGIUM_DB_FILE` pointing at a laptop) and left it registered but env-gated, on the premise that bulk-only data with a login could not reach production. Two things have changed: Phase 180's persistent disk holds the other bulk indexes, and the KBO portal — one full ZIP a month, `KboOpenData_<n>_<yyyy>_<mm>_Full.zip`, ~240 MB, nine CSVs — answers a datacentre address behind a plain Spring form login with a free account. So `scripts/build_bce_belgium_index.py` logs in (`KBO_OPEN_DATA_USERNAME` / `KBO_OPEN_DATA_PASSWORD`), picks the newest full file off the listing, requires each CSV's exact cookbook header and a floor of rows, and writes one index of the register's active entities: name per language (official over commercial over abbreviation) and every filed name of a legal person in an FTS5 search table, status, juridical situation, type and form codes with the register's own wording from `code.csv` (NL/FR/DE/EN), start date (day-first in the file), the current registered office, and KBO's `SnapshotDate` as the cut. `.github/workflows/refresh-bce-belgium-index.yml` runs it monthly and replaces the `bce-belgium-index` release asset; `warm_index()` downloads it at boot (`BCE_BELGIUM_DB_URL`); until the first run the source is not announced (`covers_lei`). The adapter is the `jar_lithuania` shape — shared read-only connection with a schema check, a note card for a number the monthly file does not hold (it holds active entities only, so a stopped enterprise reads as absent, never as dissolved), a `source_read` degradation on a SQLite error, no invented stub search row. GLEIF files 41,351 ISSUED Belgian LEIs under RA000025 with the number dotted (`0202.239.951`, 197 of 200 sampled), so the mapper now writes the `BE-BCE_KBO` identifier dotted, as the register and GLEIF spell it, and the two statements corroborate (Phase 35 wrote the ten digits and they never met); the legal form and a natural-person enterprise go to `entityType.details`, and a juridical situation other than the normal one ("Bankruptcy opened") rides as the status text and leads the finding. The register publishes no shareholders, officers or beneficial owners — the Belgian UBO register is FPS Finance's and is not open — and the finding never says "none on file". Before deploy: add the two KBO secrets and run the workflow once by hand.
