---
title: Related-party person screening goes to OpenSanctions as one batched /match.
readme: Related people are now screened against OpenSanctions in one batched match request that also sends their birth year and nationality, with every existing match gate unchanged.
tests: backend +12
---
`cross_check` used to send one `GET /search` per related person; it now sends every related person as a FollowTheMoney `Person` example — name, birth year and alpha-2 nationalities from the bundle — in one `POST /match/default` (`OpenSanctionsAdapter.match_persons`, chunks of 100, OpenSanctions' limit). The name travels as JSON, so the Lucene reserved-character bug class cannot reach this path, and OpenSanctions' `logic-v2` scorer now sees the birth date and nationality when it ranks candidates. Billing is unchanged by design: the hosted API charges `/match` per query and `/search` per request (metering FAQ, read 10 Nov 2026), so a lookup screening 25 people spends 25 credits either way; the batch saves round trips and the per-key request quota. OpenSanctions' score orders and never decides: `cutoff=0.0` returns every scored candidate, `limit=10` as on `/search`, the `match` flag is ignored, and every hit goes through the existing gates — 0.88 similarity, the single-token person guard, birth-year and patronymic conflicts, distinctive tokens — and the Phase 106 confidence ladder. A failed request is a failure for every name in it, a refused query inside a 200 batch one for that name (shaped as an HTTP error, so a 429 reads rate-limited), and both reach the `cross_source_names` degradation exactly as a failed search did. Each query's answer is cached on its own for seven days. Entities, the register-anchored subject screen and EveryPolitician stay on per-name search. After deploy: look up a company with a dozen or more related people (Equinor, Ørsted) and check the OpenSanctions related-party signals match the previous run, and that `/signalstats` shows no new `cross_source_names` degradations.
