---
title: The demo Neo4j import scripts load shares, flags and dates as typed values.
readme: The demo graph's Neo4j import scripts now load share percentages as numbers, flags as booleans and dates as dates, with a share-band weighting convention in the demo queries.
---
Regenerated `import.cypher` in `data/demo/neo4j/` and inside its twelve per-LEI zips with bods-neo4j `0e01cf1`, which replaces `LOAD CSV … SET r += row` with an explicit typed `SET` per column. `LOAD CSV` reads every cell as a string, so until now shares loaded as `"75.0"` (numeric comparisons and sorts were lexical), `isComponent` / `beneficialOwnershipOrControl` as the strings `"true"` / `"false"`, and dates as strings. Now `shareExact` / `shareMinimum` / `shareMaximum` are FLOAT, the flags BOOLEAN, `interestIndex` / `ordinal` INTEGER, and full ISO dates DATE (regex-guarded, so a malformed value is kept as its string); `birthDate` / `deathDate` stay strings because BODS allows partial dates. The CSVs are byte-for-byte unchanged (their headers match what the new generator emits), and each zip differs only in its `import.cypher`. OpenCheck's BODS was already numeric; the fault was in the import (Notion ticket "Share percentages load into Neo4j as strings"). New `data/demo/neo4j/demo_queries.cypher` sets out the share-band → weight convention the ticket asked for: keep both ends of a UK PSC band, use the lower bound for a conservative threshold test, the midpoint for centrality weights and the upper bound for "could reach", say which was used, and never weight a holding with no stated share as 0. Verified on Neo4j 5.26: the demo graph loads 520 entities / 18 persons / 666 relationship statements as before, with 355 OWNS edges (297 in the 75–100 band, 51 in 25–50, 7 in 50–75), and at 50% the lower bound counts 304 holders where the upper bound counts 355. The Estonia dataset release's Neo4j zip was regenerated the same way (a release-asset swap; `data/estonia/` is not in git). Check in production: nothing — no runtime code changed.
