Third of three steps on the "Update MCP approaches" ticket (25 Nov 2026). A full lookup can take longer than Claude Code holds a request open (a first byte within 60 seconds, five idle minutes), and a dropped call loses a check the server finished anyway. `mcp/tasks.py` implements the `io.modelcontextprotocol/tasks` extension through the SDK's `tools/call` interceptor: for a client that declared it on 2026-07-28, a call to one of the eight tools that run a pipeline starts at once and, if it has not finished within three seconds, is answered with a task (`taskId`, `status`, `createdAt`, `lastUpdatedAt`, `ttlMs` one hour, `pollIntervalMs` five seconds, and a `statusMessage` read from the lookup run's own events). `tasks/get` returns the result once complete, `tasks/cancel` stops the task's wait without stopping the detached lookup run, `tasks/update` is acknowledged, and an unknown id is -32602. The work is charged once to the caller's lookup budget; polls spend a separate MCP tier (300 a minute) so waiting on a few tasks does not spend the default one. Tasks are held in memory on the single instance: a deploy loses those in flight, which Claude Code reports as "outcome unknown" after retrying five minutes, judged acceptable. Clients that did not declare tasks, and every quick tool, are unchanged. After deploy: in Claude Code, run a fresh lookup of a large company (Shell) and check it comes back as a task and completes.
