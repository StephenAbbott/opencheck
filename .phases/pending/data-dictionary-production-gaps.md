---
title: The data dictionary's extension guard reads the BODS schema, not a prefix.
readme: The output data dictionary now documents every key OpenCheck adds to BODS, found by reading each statement against the v0.4 schema, after the post-deploy check found five undocumented in production.
---
The post-deploy check of the data-dictionary phase (4 Nov 2026) exported Unilever from production and read every statement against the vendored BODS v0.4 schema. Five keys OpenCheck writes had no entry, because the guard only looked for the `opencheck` prefix: `legalFormLabel` and `primaryIndustryCode` on `recordDetails` (GLEIF / CVR / Zefix), and `formerName`, `identityVerification` and `companiesHouseFiling` on annotations. The Slovak RPVS mapper also wrote `politicalExposure.details.type`, which is not a v0.4 field; it now writes a `reason` sentence ("Recorded by the Register of Public Sector Partners (RPVS) as a public official"). The dictionary's motivation table claimed `linking` was never written, though the PermID listing writes one; the table is now checked against an AST scan of the package in both directions. The FtM `wikidataId` and `idNumber` keys gained descriptions. The conftest mapper guard now fails any key the schema does not define at its place, whatever its name (`tests/_bods_schema_keys.py`), and the sample bundle is built with the real helpers so it carries every registered extension. After deploy: re-export Unilever (`/export?lei=549300MKFYEKVRWML317&format=json`) and confirm every non-schema key appears in `docs/data-dictionary.md`.
