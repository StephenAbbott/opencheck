From the check against Open Ownership's usable beneficial ownership data guidance (feature 14, relevant person information: name, nationalities, month and year of birth, countries of residence). Companies House files `country_of_residence` on every individual PSC and officer and the mapper dropped it, so OpenCheck published no residence for a UK person. The new `bods/residence.py` turns a filed country into `{type: "residence", country: {name, code}}` — **country only, never a street** (the Estonia rule) — and is shared so the other registers in the ticket's sweep can use it. Resolution is fixed-order and never guesses: a table of spellings registers use that pycountry does not resolve (UK nations, "Uk", "U.K.", "Untied Kingdom", "Russia", "Turkey", "Hong Kong Sar", "Republic Of Ireland"…, measured on 5,500 values in the local Companies House cache), an ISO 3166-2 code ("Gb-Eng"), then pycountry. A string that names no single ISO country ("Channel Islands", "Korea", "Kosovo", "New York") keeps the filer's words as the name with **no code**, never a stand-in, with a `commenting` annotation; where the published name differs from the filed words ("England" → United Kingdom, GB) a `transformation` annotation keeps them, so Scotland, Wales and Northern Ireland are not lost. The individual-PSC and company-officer paths read the item's field; the officer-appointments path reads the appointments, because **the envelope carries no country of residence** (nor nationality) — the latest current appointment first, then the latest resignation. **Effect on signals:** `icij_check._party_facts` reads a person's non-service address countries for the Phase 237/282 jurisdiction gate, which until now had nothing for a UK person; an Offshore Leaks person match whose ICIJ countries include the residence moves from low to medium, and one whose ICIJ countries are known and exclude it is dropped. Watch the next findings-regression report for OFFSHORE_LEAKS movements on the golden set (Regulatory DataCorp, ASDA, Quantexa are the person-heavy ones); they are input changes, not rule changes, so no stamp was bumped. Person `statementId`s move (content-addressed); `recordId`s do not.
