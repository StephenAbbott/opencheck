---
title: Every statement's `declarationSubject` names the network's subject — the looked-up company as each source records it — and the resolver stops treating it as an alias.
readme: Every BODS statement's declarationSubject now names the looked-up company as its source records it, per source, instead of each party naming itself.
tests: backend +17, vitest +1
---
Phase A of the "Improving alignment with BODS record ID requirements" ticket, prompted by the Ørsted lookup of 22 Oct 2026 where a Wikidata party read `statementId == recordId == declarationSubject`. BODS v0.4 says `declarationSubject` is "a recordId value for the subject of a beneficial ownership network" and every statement about a declared network "MUST contain the subject's recordId as its declarationSubject"; the standard's own example has a self-disclosed company naming itself and the same company, inside another's network, naming that other. OpenCheck's factories defaulted every entity and person to its own recordId and every relationship to its immediate subject, so a board member, an owner or a subsidiary each claimed to be the subject of its own network, and in a chain deeper than one layer the upper relationship named the company in the middle. Stephen's decision (23 Oct 2026): **per source** — each source bundle's statements carry that source's own subject record, so a bundle read alone (`/deepen`, the Data drawer, a per-source export) is a declared network in its own right and says the same thing inside a lookup. `bods/declaration.py` does it in two passes, one rule: `stamp_bundle` where one source's bundle is mapped (`/deepen`, `_safe_deepen`, the FullCheck register hop, the subsidiary network), finding the subject by the lookup's reference (an LEI or Phase 290's `SCHEME:id`) → an entity statement carrying the adapter's hit id as an identifier (a register bundle carries no LEI; the drawer knows only the hit id) → the only entity in the bundle → nothing, the factory default kept and the miss counted on `/signalstats` → `declaration_subject` by `source_id|outcome` (the Phase 267 rule that a miss is loud); then `stamp_merged` over the merged lookup bundle, where the reconciler's referent group names every source's subject statement at once and restamps each source's statements to its own member. Copies, never mutation; the OECD's MEIP statements and Open Ownership's stored bundles are never touched — their declarations are their publishers'. The frontend's `reconcileBods` carries the members' declaration onto a merged statement and remaps every party's to the subject's canonical id. **The resolver dropped its third tier**: `refs.py` / `bodsRefs.ts` indexed `declarationSubject` as an alias below recordId since Phase 210, which was harmless only while the subject's own statement was in the bundle — once every statement names the subject, the alias would point the subject's id at whichever party came first in a bundle lacking it. Nothing references a party by `declarationSubject` (v0.4 references by recordId); `bodsGraph.test.ts`'s fixture, which did, now references by recordId. The weekly BODS quality sweep gains `declaration_subject_not_subject` (fail): a value naming no party in the bundle, a source whose statements name more than one subject (the pre-phase shape), or a named subject that does not name itself. **Left for phase B** (content-addressed `statementId`, decided the same day): the FullCheck anchor remap is a blunt string replace that today rewrites `recordId` and `declarationSubject` along with `statementId` because the three are equal, and the entity/person `statementId` is still stable across content changes. Post-deploy: read `/signalstats` → `declaration_subject` for `unresolved` rows — the test suite's deepen paths resolved every real bundle by reference or hit id, but a source whose mapper carries the hit id under no identifier would show there; and check the next Tuesday's quality triage for the new class.
