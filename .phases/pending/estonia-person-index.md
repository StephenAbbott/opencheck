title: Estonia: a person's other companies on the register, keyed on the register's pseudonymous person key — listed on demand, never a name search, and one node per same-named person on the page fallback.
readme: An Estonian officer, shareholder or beneficial owner now shows the other companies the e-Business Register names them on, keyed on the register's own person key.
tests: backend +25, vitest +8, vitest_files +2
---
The e-Business Register publishes `isikukood_hash` — the same UUID for the same natural person on every list of every company — so re-users can follow a person across companies; until now OpenCheck used it only to make one person one node within one company. The index builder adds a partial index on the hash to each of the four people tables (no schema bump: an index built before them answers by scan until the daily rebuild), `ariregister.companies_for_hash` reads every current row naming the key, and `GET /person-appointments?scheme=EE-ARIREGISTER-HASH&id=<uuid>` answers in the Companies House officer-appointments shape: company, form, status, which list (registry card, shareholders, beneficial owners, outside the card), the role in the mapper's own words, since, and the share — no addresses, at most 500 rows with the total counted. Stephen's decisions (16 Oct 2026): keyed on the hash only, never a name search (a non-UUID is a 400, a personal code's shape refused); the fields the register publishes; listed, never drawn as graph nodes. A hash on no list is an empty list; no index is a stub answer that says so. The caveat states that the hash is pseudonymous and not an identifier, that the register does not guarantee one key per person, and that the files are current rows only, so a deleted company or an ended role is not listed. "Companies on the Estonian register" sits on a BackgroundCheck card and on an Estonian person statement in the Data drawer, fetches on click, and is absent on a saved report. MCP gains `opencheck_person_positions(scheme, id)` (the Estonian key, or a Companies House officer id), on the lookup tier. The page fallback has no hash, so one company's same-named natural persons — case, accents, hyphens, spacing and a Nasdaq CSD account prefix set aside — become one node, named with the registry card's spelling, with a `commenting` annotation saying which lists were joined and why. After deploy and the next index rebuild: check a person on two companies (the ticket's Veronika Oškina example) lists both, and note the index asset's growth from the four hash indexes.
